## 0. 一句话概括

做一个 **Tauri v2 移动端优先**的 **AI 多 Agent 协作写作 App**：抛弃 SillyTavern「预设 + 世界书提示词注入」的单提示词范式，改用 **多 Agent 显式编排**联合写文；**新项目**（不 fork TT/ST，借 TT 架构思路，砍掉用不上的功能）；**重写一个简洁清新的前端**；后端**原生集成**小白X 的总结 / 推进剧情 / 向量化能力；**兼容 ST 角色卡导入**（含蓝灯/绿灯世界书）、**ST 预设导入**（含 spreset 式正则）、**带前端的角色卡渲染**（参考酒馆助手 / JS-Slash-Runner），以及**原生兼容 MVU 变量框架**（导入含 MVU 的卡即可用，操作逻辑不变）。

**产品形态再明确（D30+）**：角色卡多为「赛博跑团」式——一卡多角色，含 NPC/场景/事件。因此 App 需支持**角色子 Agent 隔离**（每个角色只看到它该知道的信息）、**多会话隔离**（一张卡多个独立游玩档）、**剧情总结 + 角色知识抽取**（成文后自动维护各角色可见信息）。

### 1.1 角色子 Agent / Campaign / MVU 兼容（D30-D44，2026-06-15 新增）

> 这批决策源于对「赛博跑团式角色卡」的深化理解：一张卡 = 一场跑团 = 多角色 + 多会话 + 信息差。
> 详细方案见 `TECHNICAL_DESIGN.md` §16-§20；Agent 接口位置见 `AGENT_INTERFACES.md`。

| # | 议题 | 决策 | 来源 |
|---|------|------|------|
| D30 | 子 Agent 定位 | **上下文隔离容器**，不是对话接口。子 Agent 只和导演通信，玩家不直接调用。两个目标：信息隔离（角色只知它该知的）+ 人设保持（不被叙事腔污染） | 用户 v6 |
| D31 | 角色知识边界 | 每个角色维护**可见信息列表**（character_knowledge）。来源四元分类：`witnessed`（亲眼）/ `told_by_other`（被告知，记来源角色）/ `inferred`（推断）/ `backstory`（背景） | 用户 v6 |
| D32 | 角色模型 | **树形**：`CharacterCard`（卡本体）下挂多个 `Character`（卡内角色），**扁平一层** + 附加参数（如「主角团」标签）。一卡多角色是常态 | 用户 v6 |
| D33 | 多角色识别 | **独立角色识别 Agent**（导入时跑）：语义级分析卡内容，识别卡内角色，为每个角色生成 `persona_prompt` + `behavior_rules` + `backstory`。不靠正则/字段硬解析 | 用户 v6 |
| D34 | 运行时新角色 | 用户可在游玩中引入卡里没有的新角色（"一个叫老王的路人走过来"）。**是否创建由导演在 Plan 时决定**，导演自主补全 persona，不打断用户 | 用户 v6 |
| D35 | 常驻 vs 临场角色 | **区分**：常驻角色（卡自带 + 用户明确确立的）进向量库长期累积；临场角色（龙套）只存会话临时区，不污染永久角色表。导演建角色时标 type | 用户 v6 |

| D39 | 角色知识存储 | **进现有 infra-vector 向量库**，打 `owner_character_id` + `campaign_id` 标签，注入时按标签过滤。零新基础设施 | 用户 v6 |

## 2. 多 Agent 写作架构（D3 展开）

```
用户输入写作意图（场景/目标/角色）
            │
            ▼
┌────────────────────────────────────────────┐
│  主 Agent ① 「导演 Director」               │
│  · 解析用户写作意图                          │
│  · 从资料源（角色卡/世界书/向量化记忆）取材   │
│  · 拆解为各角色的子任务                      │
│  · 为每个子 Agent 构造「专属上下文包」        │
│    （只含该角色所需设定，互不污染）           │
│  · 输出：任务分发计划 + 各子 Agent 上下文     │
└──────────────────┬─────────────────────────┘
                   │ 并行派发（可批可流）
        ┌──────────┼──────────┬──────────┐
        ▼          ▼          ▼          ▼
   子Agent(角色A) 子Agent(B) 子Agent(C) …
   各自产出该角色的行为/对白/心理（并行）
   各自独立上下文，可独立取消
        └──────────┬──────────┴──────────┘
                   ▼
┌────────────────────────────────────────────┐
│  主 Agent ② 「编剧 Editor」                 │
│  · 收集所有子 Agent 产出                     │
│  · 合并 · 润色 · 节奏把控 · 输出最终成文      │
│  · （可能）回写记忆/总结到资料源              │
└────────────────────────────────────────────┘
            │
            ▼
       最终成文（展示给用户）
```

**移动端交互要点（待确认，见 §6）：**
- 子 Agent 数量按场景内出场角色**动态决定**
- 主/子 Agent 用**不同模型**（子可廉价，主用强模型）
- 用户可**中途打断 / 改派任务 / 预览任一 Agent 产出**

## 3. 资料源体系（D8 + D9 + D4 的交汇点）

这是整个系统的"数据底座"。**关键认知**：ST 用预设/世界书做提示词注入，我们不注入——而是把这些数据当作**Agent 可检索的资料库**。

### 3.1 角色卡（ST V2/V3 兼容导入）
- **来源格式**：PNG（embed JSON） / 纯 JSON / V3 卡
- **解析字段**：`description` / `personality` / `scenario` / `first_mes` / `mes_example` / `alternate_greetings` / `character_book`（内嵌世界书）/ `extensions`（HTML 代码等）
- **导入后**：结构化存储，供导演 Agent 取用

### 3.2 世界书（蓝灯/绿灯结构）
- **蓝灯（constant=true）**：永远激活，作为世界观常驻设定
- **绿灯（constant=false, selective）**：关键词触发，按需激活
- ⚠️ **范式转换**：ST 把激活条目拼进 prompt；我们改为——蓝灯条目进导演 Agent 常驻上下文，绿灯条目进**向量化检索池**，由 Agent 主动查询。

### 3.3 预设（含正则）
- **导入格式**：ST preset JSON（含 prompt manager / 聊天补全 prompt 列表）
- **spreset 式正则**：preset 内嵌 `extensions.regex_scripts`，导入时一并解析为**输出/输入正则规则**（用于角色名替换、格式清理等）
- ⚠️ **用途定位**：预设**不再决定 prompt 结构**（那是 ST 范式），而是作为——
  - Agent 系统提示词的**可选模板**
  - 正则脚本的**载体**
  - 导入兼容性使老用户无缝迁移

### 3.4 向量化记忆（小白X 原生化）
- **核心算法 Rust 重写**：分段 → 嵌入 → 向量存储 → 相似检索
- **触发**：导演 Agent / 编剧 Agent 的工具调用
- **前端入口**：总结合能开关、查询已有总结（D5）

## 4. 带前端角色卡渲染（D6 + D7）

**问题**：很多 ST 角色卡带 HTML/JS 前端（互动界面、状态面板），靠脚本注入 ST 运行。
**方案**：参照酒馆助手，**iframe 沙箱 + postMessage + 受控 API 桥**。

```
新前端中每个角色卡渲染区 = 一个 iframe
   ├─ srcdoc = 角色卡的 HTML/JS/CSS
   ├─ sandbox 限制（no same-origin, allow-scripts）
   └─ postMessage 通道
        ├─ 卡 → 宿主：调用受限 API（getCharData/setVar/getChatLog…）
        └─ 宿主 → 卡：推送事件（新消息/变量变更/状态更新）
```

**需桥接的 API 子集**（参照 JS-Slash-Runner，待裁剪）：
- 变量读写（`getVariable` / `setVariable`）
- 角色信息（`getCharacters` / `getChatMessages`）
- 角色卡内嵌资源解析（asset URL 改写）
- 受限事件订阅

**安全**：iframe 沙箱 + CSP + 白名单 API，防止恶意卡逃逸。

## 5. 技术栈（默认假设，可改）

| 项 | 选择 | 理由 |
|----|------|------|
| 框架 | Tauri v2 | 移动端 + 复用 TT 经验 |

| 嵌入模型 | 远程 API（OpenAI/SiliconFlow）或本地 ONNX | 待定 |

## 7. 我评估的四大技术风险（先告诉你）

1. **移动端多 Agent 并行成本**：N 个子 Agent 并行 = N 倍 token / 延迟 / 发热。需"廉价模型跑子 Agent + 强模型跑主 Agent"策略，以及"按需启动子 Agent"。
2. **"专属上下文包"的构造**：导演 Agent 要为每个子 Agent 准备不污染的上下文——本质是**信息检索/分配问题**，正好和向量化耦合，要一起设计。
3. **ST 数据格式的兼容深度**：角色卡 PNG embed、世界书蓝绿灯、spreset 正则，每层都有边角情况。需尽早建**导入兼容性测试集**（用真实角色卡/预设跑）。
4. **iframe 沙箱角色卡的安全性 vs 兼容性**：API 桥越全越兼容，但攻击面越大；沙箱逃逸、资源改写要严控。
